## 7. Ablation on Run C logs

Computed offline from Run C's logs — no new runs (`analysis/replay.py`, applied per run, pooled over the 5). Detection uses the same definition as the full evaluation (flow level, or its host pair while active, >= CLONE).

- **(a) IF only** — the logged per-window raw IF levels (flow and host-pair models) replayed through the controller's own hysteresis (`controller/policy.FlowPolicy`), every DPI confirmation ignored; no flow-head clones (N = 0); adaptive sampling kept (it feeds the IF's payload-entropy feature, Decision C).
- **(b) DPI-head only** — no IF: raw level NORMAL every window; each logged DPI confirmation attributable to a flow-head clone (clone_reason 4, or 3 under a host-clone rule that a DPI-head escalation installed) force-clones the flow, and for syn/null scans its host pair, at the poll that processes it, then de-escalates by the same hysteresis; head clones kept (N = 3); no sampling. Confirmations used: reason 3 dropped: 34, reason 3 kept: 152, reason 4 kept: 1112.
- **(c) full system** — the logged run as it happened (`analysis/evaluate.py`; inspection from the data-plane counters).

| configuration | TPR [95% CI] | FPR [95% CI] | inspection reduction (packets) |
|---|---|---|---|
| IF only | 0.108 [0.088, 0.131] | 0.066 [0.045, 0.092] | 62.9% (estimated) |
| DPI-head only | 0.857 [0.832, 0.880] | 0.057 [0.038, 0.082] | 94.8% (estimated) |

**What IF-only detects.** Its 91 detected attack flows come from null_scan 24/320, rate_spike 27/40, syn_scan 40/320 (`per_class` in `numbers.json` → ablation): the flow model catches the rate spike, and the host-pair model catches some scan probes (in the full system most of those probes are credited to DPI-head instead, because a DPI-head escalation fires first and the trigger attribution takes the flow's own escalation before its host pair's). SQLi is never caught without DPI (0/160).

**What IF adds on top of DPI-head** (full system − DPI-head only; inspection compared estimate-to-estimate, since (b) has no measured counters):

| | DPI-head only | full system | Δ (full − DPI-head) |
|---|---|---|---|
| TPR | 0.857 | 0.899 | +0.042 (+35 attack flows) |
| FPR | 0.057 | 0.079 | +0.021 (+10 benign flows) |
| inspection reduction (estimated) | 94.8% | 59.0% | -35.7 pp |

Per class, attack flows detected (DPI-head only → full system): null_scan 312 → 320, rate_spike 0 → 27, sqli 160 → 160, syn_scan 248 → 248. (Measured full-system inspection reduction: 59.6%.)

**How far to trust (a) and (b).**
- *Level replay:* on flow slots and host pairs that no DPI action ever touched, the IF-only replay reproduces the logged level on 99.89% of flow rows and 100.00% of pair rows, and replaying the logged levels reproduces the full system's per-flow detections exactly. Every benign flow (b) flags is also flagged by the full system (27 of 27; there they were credited to IF-flow, which takes precedence in the trigger attribution), and (b) detects no attack flow the full system missed (0).
- *Inspection estimate:* the clone estimator, run on the full system's logged levels, matches the measured data-plane counters to within -0.7% to +2.3% of total clones per run (forwarded packets within 0.03%); (a) and (b) use the same estimator.
- *Not captured:* the traffic, the IF scores and DPI's own decisions are the logged ones. With a different clone stream DPI could decide differently — e.g. without sampled iperf3 clones, its syn-scan ratio rule (suppressed by them in Run C, see RESULTS.md) might fire more often in (b). (b) is therefore a lower bound on what a DPI-head-only system would confirm, not an exact replay.

## 9. Exact parameter values

### Thresholds (per run)

One flow model and one host-pair model per run, **shared by both switches** (`controller/monitor.py` builds a single `FlowIsolationForest` and `HostPairIsolationForest`, `controller/monitor.py:121`), trained once on warm-up vectors from both switches — so there are no per-switch thresholds; the values below apply to s1 and s2 alike. **p5 = 0 in every run** (to floating-point precision) because the MONITOR threshold coincides with sklearn's `contamination = 0.05` boundary: `IsolationForest.decision_function` is the raw score minus `offset_`, and `offset_` is set to the 5th percentile of the training scores when contamination = 0.05. The warm-up 5th percentile of `decision_function` is therefore 0 by construction — the MONITOR threshold is exactly the boundary sklearn itself would use to call a sample an outlier. The CLONE threshold (p1) is the only one that varies by run.
